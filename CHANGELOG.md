# Changelog

## 0.4.0

**Upgrade note – read before updating.** This release adds two entities to the database (`TagDefinition`, the tag register, and `TagAlias`, its alternative names). As soon as the new server has opened your store, 0.3.x binaries can no longer open it (ObjectBox refuses with "DB's last entity ID … is higher than … from model"). So: back up `~/.remembox` first; stop every process that uses the store (quit every Claude window, stop any daemon) before the first start of the new version, so no 0.3.x process is still attached; a downgrade is only possible by restoring that backup. If you use Sync, upgrade every device together and re-run `tool/sync-server/run.sh` so the sync server picks up the new model file. Every existing entity is unchanged.

- **Strict registry mode (`OBX_MEMORY_REGISTRY_MODE=strict`).** Project names and tags can now be enforced instead of only suggested. In strict mode `remember`, `supersede`, `fact_set` and `entries_move` reject a project that has no registry row or was merged into another one (archived projects stay writable), and `remember`/`supersede` reject any tag that is not registered – nothing is written, the error names similar registered names and how to register a new one, and the server logs one `[registry] strict: rejected …` line. `project_set` then needs a description to create a project and rejects a name that differs from a registered one only by case/space/-/_ unless `allowSimilar: true` is passed; `project_merge` needs a registered `into`; `tag_merge` needs a target that is registered or receives a definition. The default, `open`, behaves exactly as before on every write path (apart from the additive result fields and warnings listed below). The mode is per process and logged at startup; an unknown value stops startup. Migration checklist for an existing store: usage guide, "Strict registry mode".
- **New tool `tag_define`:** registers a tag with a one-sentence description (or updates the description). The name is normalized like a tag on `remember`; a name that repeats a project (active or archived – a merged-away project name is a tombstone and does not block a tag), a kind or an area is rejected, and so is a spelling variant of a registered tag (case, plural, separators) unless `allowSimilar: true` is passed. Unknown arguments are rejected. Works in both modes.
- **Tag aliases.** `tag_define` takes `aliases`: alternative names of a tag – old spellings, synonyms, other languages (e.g. `chores` for `housework`, `recipe` for `cooking`). A write that uses an alias stores the tag, in both modes, with a warning (`Tag "chores" is an alias of "housework" – stored as "housework".`). `aliases` replaces the tag's aliases; `addAliases`/`removeAliases` change single ones, and every removed alias is named in a warning. An alias that is the tag itself, another registered tag, an alias of another tag or a project/area/kind name is rejected, and so – unless `allowSimilar: true` – is a spelling variant of another tag or alias (and a new tag that is a variant of an alias). An alias whose tag is not registered is not resolved (warning; `tags_list` flags it `aliasTargetMissing`). `tag_merge` into a registered tag records the merged-away names as aliases (`aliasesAdded`) and moves the aliases of merged-away tags; a merge into an unregistered target records none and – once any tag is registered – warns about it, also in open mode. A `tag_merge`/`tags_normalize` target that is an alias means its tag. `tag_remove` removes a tag's aliases (`aliasesRemoved`) and points at `removeAliases` for a name that is only an alias. `tag_merge`, `tag_remove` and `tags_normalize` report `aliasesAdded`/`aliasesRemoved` in both modes. Migration order: `tag_define` every kept tag and merge target, `tag_merge` the synonyms (dry run first), `tag_remove` the rest, then expect `unregisteredInUse: 0` and `aliasesInUse: 0` in `tags_list`. `tags_list` shows `aliases` on registered rows and `aliasOf` on aliases in use, its `prefix` also matches aliases (`matchedAlias`), and it reports the number of `aliases` and `aliasesInUse` (alias names entries still carry); `stats.registry` adds `tagAliases`. Strict rejections also suggest the tag behind a similar alias. New entity `TagAlias` (covered by the upgrade note above). Projects get no alias field – a merged project name already acts as one. Note: aliases resolve before the project/kind/area redundancy check, so if an alias name later also becomes a project name, a tag with that name is stored as the alias's tag instead of being dropped as redundant.
- **`project_set` accepts `allowSimilar`** (strict mode only; ignored in open mode).
- **New result fields** (additive, in both modes): `tags_list` rows carry `registered` and `description`, registered-but-unused tags are listed with count 0, registered tags sort first within one count, and the result adds `registryMode`, `registered` and `unregisteredInUse`. `areas_list` adds the project register – `projects` (name, status, description, areas), `mergedProjects` (name, mergedInto) – and `registryMode`. `stats.registry` adds `mode` and `tagDefinitions`. `tag_merge` reports `definitionsRemoved`, `intoDefinition` (`kept`, `carried` or `none`) and `carriedFrom`; `tag_remove` and `tags_normalize` report `definitionsRemoved`. `reindex` reports newly registered project names that differ from another registered name only by case/space/-/_ (`registry.nearDuplicates`, plus a `warning`).
- **Tag maintenance keeps registrations consistent:** `tag_merge` (and `tags_normalize`) carries the description of a registered `from` tag over to an unregistered target and removes the `from` registrations; `tag_remove` removes the registration with the tag. A name that has a registration but no tag row is no longer reported as `notFound`. A definition is only carried to a target `tag_define` would accept (not a project, kind or area name, not a variant of another registered tag): strict `tag_merge` rejects such a merge with nothing changed; open `tag_merge` and `tags_normalize` merge without the carry and say why in a new `warning` (`intoDefinition: none`). In strict mode `tags_normalize` also warns about a target that stays unregistered.
- **`remember` and `supersede` now suggest links.** The result carries `related`: up to five existing live entries that are semantically close to the one just written (same project first, never superseded or expired ones, only above a similarity bar of 0.86 on the `recall` scale), each with `id`, `title`, `project`, `kind`, `similarity` and `createdAt` (and `externallySourced: true` for url/file entries), plus a `relatedHint` on how to link or supersede and the usual `_provenance_note` marking the titles as untrusted stored text. Entries at 0.90 or above carry `likelySameThing: true`: they are probably an older state of what you just wrote, so `supersede` (prose) or `fact_set` (exact value) fits better than a link. Further candidates above the bar are never dropped silently: `relatedMore` counts them (`relatedMoreIsLowerBound: true` when the candidate search was saturated and the count is only a minimum – `relatedMore` can then even be 0, with an explanatory `relatedHint`; `recall` lists them all). If no same-project entry reaches the bar, the single nearest live same-project entry at 0.80 or above is still offered as the first item, marked `weak: true` (never `likelySameThing`; it takes one of the five slots and is not counted in `relatedMore`): in an end-to-end check, short follow-ups to long originals often scored 0.80–0.86 against their predecessor. The entry being superseded is never listed. The keys are absent when nothing qualifies and the search was not saturated; if the search fails the write still succeeds and the result's `warning` says so. The 0.86 bar was measured on real entries with the default embedder (embeddinggemma): two independent raters labelled 67 pairs (kappa 0.81); every pair at 0.86 or above was judged useful, below it a large share was noise, and every "older state of the same thing" lay at 0.86 or above, most at 0.90 or above. It may not fit another model set via `OBX_MEMORY_EMBED_MODEL`.
- **`remember` accepts `links`:** a list of `{toId, type, note?}` (at most 10) created in the same transaction as the entry. An unknown `toId` or link type, more than 10 items, an over-long note or an unknown key in an item rejects the whole call and nothing is written.
- **Setup templates: cockpit, Instructions for Claude block, global CLAUDE.md.** A new `templates/` folder, shipped in the release ZIP next to the skill: `cockpit.md` (a fictional example of the "Now" layer – sections, state markers, weekly review), `instructions-for-claude.md` (the short always-loaded block) and `global-CLAUDE.md` (the long-form rules for `~/.claude/CLAUDE.md`). The templates are in English. README, usage guide and both quickstarts point to them; a test keeps every copy of the short block identical.

## 0.3.1

**Bug fix – back up `~/.remembox` first, as with any upgrade.** A write could fail permanently with an error like `Entity unavailable for indexed ID 225` (`DbFileCorruptException`, `OBX_ERROR` 10502), and the tag, project or area name involved became unusable forever – every later attempt to store that exact name failed the same way. Cause: unique string properties (tag names, project names, area names, and a few internal identity keys) were indexed as a 32-bit hash instead of by their real value; a write's uniqueness check on a hash index has to look up the matching bucket and load each candidate row by id, and if that row was already gone – a stale index entry – the load failed and took the whole write down with it.

Fixed by switching every `@Unique` string property to a value index, which keeps the real value in the index, so the uniqueness check should no longer need the by-id lookup that failed (our reading of the mechanism – ObjectBox does not document the value-index path); with replace-on-conflict a genuine match is still found and replaced. No manual step is needed: opening an existing store with 0.3.1 rebuilds the affected indexes, because their type changed. That rebuild is not documented by ObjectBox; it was observed on objectbox 5.3.2 / macOS arm64, where opening an affected store once with 0.3.1 removed the stale entries – hence the backup advice above. No data was lost in that test. One caveat for the rare case of a store that already holds two rows sharing one of these values: rebuilding a unique index is expected to refuse the store open (not tested) instead of repairing it – restore the backup and report it.

**If you use Sync, or otherwise run more than one remembox process against the same store:** every open rebuilds these indexes to match whichever build opened the store last – an old (0.3.0) build reopening after a new (0.3.1) build rebuilds them back to the hash index, and a 0.3.1 build reopening after that rebuilds them to the value index again, in either direction. Quit every running client (Claude Code, Desktop, Cowork, any daemon) before installing 0.3.1, and re-run `tool/sync-server/run.sh` so a sync server picks up the new model file, so only the new build opens the store afterwards – the same rule as any other upgrade, just worth repeating here since old and new builds would otherwise keep flipping the index type back and forth on every open.

- The Claude skill now lives in the repo at `skill/SKILL.md` (previously assembled only at release time from a maintainer-local file) and covers the 0.3.0 areas, facts and tags tools alongside the original recall-first / remember-after loop.

## 0.3.0

**Upgrade note – read before updating.** 0.3.0 adds four entities to the database. As soon as a 0.3.0 server has opened your store, a 0.2.x server can no longer open it (ObjectBox refuses with "DB's last entity ID … is higher than … from model"). So: back up `~/.remembox` first; quit every Claude window (and stop any daemon) before the first 0.3.0 start, so no 0.2.x process is still attached; a downgrade is only possible by restoring that backup. With Sync, upgrade every device and restart the sync server together. After the update, run `reindex` once (registers existing projects) and `tags_normalize` once (dryRun first).

Adds areas and facts on top of free-form memories.

- **New tools:** `area_set` / `project_set` (create or update an area, or a
  project's description, status and area membership), `areas_list` /
  `project_merge` (inspect the registry and its health, merge a duplicate
  project name into another), `fact_set` / `fact_get` / `fact_query` /
  `fact_forget` (exact, structured values keyed by project + subject +
  attribute, with automatic history).
- **`area` filter** added to `recall`, `list_recent` and `fact_query` –
  matches every project assigned to that area.
- **`stats`** gained a `facts` block and an `byArea` breakdown alongside the
  existing `byProject`.
- Schema change is additive only: four new entities (`ProjectScope`, `Area`,
  `AreaMembership`, `Fact`); every existing entity is unchanged.

### Upgrade steps

1. Restart all Claude sessions (Claude Code, Desktop, Cowork) after updating
   so they pick up the new binary and tool list.
2. Run `reindex` once – besides its usual vector-index repair, it also
   registers every project name already used on existing entries and facts
   that has no registry row yet, so `areas_list` and area filtering see the
   full picture from the start.
3. If you use Sync: upgrade all devices and restart the sync server before
   relying on the new entities across more than one device – a device still
   on the 0.2.0 model does not know about `ProjectScope`/`Area`/
   `AreaMembership`/`Fact` and cannot write them.

- Date and time arguments (`expiresAt`, `docCreatedAt`, and the fact tools' `valueDate`, `validFrom`, `at`, `validUntil`) are parsed strictly: a bare date (`YYYY-MM-DD`) means UTC midnight, a date-time must carry `Z` or an explicit offset, and a date that does not exist (e.g. `2030-02-30`) is rejected instead of being rolled over.
- Fact history never overlaps: a new value closes every value that would still be valid at its start; a value cannot be inserted before an existing or scheduled one (the error names the scheduled fact and how to cancel it).
- **Tag discipline:** `remember`/`supersede` now normalize every tag to camelCase (`apps-script` -> `appsScript`), drop tags redundant with the entry's project/kind/area (with a warning), and warn (without rejecting) about near-duplicates of an existing tag, more than five tags on one entry, and identifier/version-shaped tags – the tool result's `warning` always says what changed. **New tools:** `tags_list` (usage counts, variant groups, unused count – check before inventing a new tag), `tag_merge` / `tag_remove` (bulk tag-graph cleanup, both `dryRun`-capable and idempotent).
- **New tool `entries_move`:** moves selected memory entries (by id) into a different project, to split a catch-all project – `project_merge` moves a whole project, `entries_move` moves only the ids you name. Pulls each id's full supersede chain along by default (`includeChain: false` to move only the given ids), never touches facts, and is `dryRun`-capable like `project_merge`.
- **Tag write path now rejects control characters outright:** a raw tag containing any control character (`U+0000`-`U+001F`, `U+007F`) is dropped before normalization, with a warning – it used to survive normalization and be stored with the raw control bytes intact (only the log line was sanitized).
- **Tag normalization fixes:** digit-led tags now normalize in one stable pass (`2026 Q3` -> `2026q3`, `3 D Printing` -> `3dPrinting`), and an acronym pluralized with a trailing `s` normalizes as one word instead of being mangled (`APIs` -> `apis`, not `apIs`) – both are idempotent, re-normalizing the stored form changes nothing.
- **New tool `tags_normalize`:** a one-shot upgrade helper for stores written before 0.3.0 – merges every tag whose stored spelling predates today's camelCase rule (e.g. `apps-script` -> `appsScript`, `KPI` -> `kpi`, `APIs` -> `apis`, `2026 Q3` -> `2026q3`) into its normalized form, in one pass. `dryRun: true` first, like `tag_merge`/`tag_remove`; safe to re-run (a second run finds nothing left to change).
